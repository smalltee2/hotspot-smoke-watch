# SEA-HAF

Southeast Asia Hybrid Air-quality Forecast: a hybrid physics–statistics–machine-learning PM2.5 forecast for mainland Southeast Asia (formerly "Hotspot Smoke Watch"; the repository name and site address are unchanged).

Hourly PM2.5 warning page for Northern Thailand and mainland Southeast Asia.

- **Total PM2.5 forecast**: CAMS global forecast (via Open-Meteo), corrected every hour against reference monitors on OpenAQ with a per-station Kalman filter on log-ratio bias, spread between stations by inverse-distance weighting.
- **Fire smoke**: VIIRS hotspots from NASA FIRMS → FRP-based PM2.5 emission (Wooster et al. 2005; Akagi et al. 2011) → Gaussian puff dispersion with Open-Meteo forecast winds (Briggs 1973 σ, Heffter 1965 long-range σy).
- **Warnings**: towns and stations banded on Thailand's PCD PM2.5 scale (1 June 2023).
- **Verification**: forecasts are logged and scored against later observations by lead time (`data/verify.json`).
- **Multi-year station background** (`scripts/climatology.mjs`, workflow `climatology.yml`, built once by hand): the last 3 years of PM2.5 of every reference monitor from the OpenAQ archive on S3 (for the Air4Thai stations, OpenAQ's copies, which hold 24-h running means: the month level is right, the hour of day is flattened; the Air4Thai history service keeps only 2–3 months and fills in only stations without a copy) summarised by month and hour (mean and 90th percentile) in `data/static/pm-clim.json`. The correction v2 reads them as two inputs (`lnClimMH`, `lnP90MH`), so it starts the burning season knowing what each station usually measures then instead of nothing; its experts still decide, from the daily check, how much to use them.
- **Compared with IQAir** (`scripts/iqair.mjs`, page layer *AQI compared with IQAir (now)*): IQAir's real-time US AQI for 17 Thai cities and 10 in Laos, Cambodia, Myanmar, Vietnam and Malaysia (AirVisual API, free Community plan: city AQI only, no forecast; 9 cities per hourly run in groups of 5 a minute apart, run beside the other steps, so each city about every 3 h, about 6,700 calls a month; key in the `IQAIR_API_KEY` secret, never logged). IQAir is the reference: the labels give the share of hours over 7 days in which our 1-h forecast at the nearest forecast point (within 15 km) fell in the same Thai concentration band as IQAir (`accuracy.json` `iqair`, `scoreIqair` in `scripts/accuracy.mjs`), and the tooltip the values now beside our map. Agreement with IQAir, not accuracy against measurements. Data credited to IQAir.
- **Hindcast expert** (`scripts/hindcast.mjs`, trained once by `scripts/hindcast_train.mjs` into `data/static/hc-model.json`): gradient-boosted trees learned from three burning seasons (18 Dec – 30 Apr of 2023/24–2025/26) of archived CAMS forecasts paired with Air4Thai 24-h means (branch `hindcast`, `data/hindcast/`; contains modified Copernicus Atmosphere Monitoring Service information). In a leave-one-season-out test it cut the RMSE of the CAMS 24-h mean 2–3 days ahead from 17–25 to 14–15 µg/m³ and caught 61–68 % of days >= 37.5 instead of 25–52 %, with fewer false alarms than persistence. It joins the self-learning correction as one more expert (CAMS run only, active 18 Dec – 30 Apr), fixed rather than retrained; the daily scoring gives it weight only while it helps.
- **Pull of long-lead forecasts toward the climatology (prepared, off)**: forecast skill falls with lead, so days 3–5 may do better pulled toward each station's usual value for the month and hour, ln(B+1) = (1−w)·ln(F+1) + w·ln(C+1). The runs log the published forecast and the climatology every 3 h at leads 24–120 h (`climfc-*.csv`, CAMS and SILAM separately); `scripts/fit_clim_blend.mjs` fits w by lead and keeps it only where it catches at least as many hours ≥ 37.5 µg/m³ with no larger false-alarm share. `CFG.climBlend` stays zero until then; applying the weights (station forecasts and map) is added once the fit gives non-zero ones.
- **Second forecast model, SILAM, through the same chain** (`scripts/silam.py`, `scripts/silam.mjs`, `scripts/silam_chain.mjs`): the FMI SILAM global air-quality forecast (0.2°, hourly, about 5 days per daily run; open data on AWS S3, CC BY 4.0). Its NetCDF-4 files are read by one Python step (netCDF4, installed only when a new run is to be read); the crop of our box is kept on the `history` branch (`silam-YYYYMMDD.json`). Then `silam_chain.mjs` runs `update.mjs` a second time with `HSW_MODEL=silam`: the same program with SILAM in the place of CAMS, so SILAM gets the steps CAMS gets (Kalman filters, station forecasts, self-learning corrections v1/v2, 0.025° map correction, forecast logs). The two runs are kept apart: SILAM's filter and learning state rides in `state.json` as `silamState`, its logs go to `data/history/silam/` and `data/mltrain/silam/`, its page files to `data/silam/`; the measurements are read back from the replies the CAMS run kept (`HSW_HTTP_CACHE`), and the model-independent steps (radar, observed rain, temperature, weather learning) are left to the CAMS run. On the admin page (`/dev.html`; the public pages show CAMS only), *Total PM2.5 forecast from SILAM (~5 days)* loads `data/silam/latest.json` in the place of `data/latest.json`, so the whole page (map, warnings, summary) shows the SILAM-based forecast; the accuracy card stays CAMS until SILAM is scored.
- **How right the forecast has been, on the public page** (`scripts/accuracy.mjs` → `data/accuracy.json`, rebuilt every run): the published hourly PM2.5 forecast against the hourly reference monitors over the last 7 days, per monitor, in three horizons (next hours: issued 1, 3, 6 h before; next day: 12, 24 h before; two days ahead: 48 h before, shown as one line under the table; pooling all leads would flatter the score, since the 1-h forecast is close to the latest measurement). The page shows Thailand only (outside it there are too few hourly reference monitors; one in Nov 2026) and sums the monitors for *here* (the nearest monitor within 25 km, else the Thai region), a Thai region (the TMD regions of the region menu) and Thailand, and shows the share of hours in the right Thai PCD colour band, the typical error (MAE), the tendency (bias) and, on the admin page only, how many hours ≥ 37.5 µg/m³ were warned in time and how many warnings did not happen. The same colour-band score is also given on the daily mean (24-h, the Thai AQI basis): the published 24-h mean forecast 24 h and 48 h before against the measured 24-h mean (≥ 18 measured hours), only at those two leads, since at shorter ones the 24 hours are partly measured already (one line under the table, and in the card's heading). Shown in the *Warnings* tab (*How right has the forecast been?*), in the *My location* card, and as an optional map layer of badges at the monitors (*Show on map*). Low-cost sensors are left out of these numbers and scored apart (`accuracy.json` `lowcost`): the OpenAQ low-cost sensors that pass the pipeline's 30-day neighbour check (`qc` in `latest.json`), all countries, summed for the area shown; one line under the map layer *Forecast accuracy at monitors* on the public page (next day and daily mean, with an (i) note), every horizon under the card's table on the admin page. They read high in humid air and the forecast at each sensor is corrected with its own readings, so this is closeness to the sensors, not to the true value.
- **Rain, the same way as PM2.5** (`scripts/radar.mjs`): the weather radar is the dense observation. Hourly, the last 2 h of RainViewer frames over Thailand (Thai Meteorological Department radars) are decoded (Universal Blue colours → dBZ → Marshall–Palmer rain rate) and averaged to 0.025° cells; the hourly means are scored against the ThaiWater gauges (adjustment factor gauge/radar over 7 days), replace ECMWF rain in the meteorology used by the smoke model where a radar sees, feed the ML rain experts as the truth (`rainobs-*.csv` column `radar_mmh`), and are published to the page (`rain-obs.json`, field `radar`). The latest frame is extrapolated along the echo motion (block cross-correlation) for 3 h. For 3–48 h the radar corrects ECMWF the way the monitors correct CAMS: every hour ECMWF is compared with the radar over the last 72 h for its timing (how many hours late its rain comes) and amount (a 0.25° radar/ECMWF factor field), and the page can blend ECMWF read later, ECMWF × the factor and the radar of the same hour on the latest observed day (diurnal persistence) by lead (`CFG.rainBlend`). The weights come only from `scripts/fit_rain_blend.py`, run on the station log `rainfc-*.csv` (every 3 h, all members by lead) against the radar truth in `rainobs-*.csv`: the first fit (15 Oct – 8 Nov 2026) kept the blend at leads of 1–2 h; from 3 h on the weights are zero (ECMWF alone caught more rain hours there). It is refitted monthly. The ML rain experts already take the radar as truth and as their recent-rain inputs. Outside radar coverage (Laos, Myanmar, Cambodia) nothing changes.
- **Observed satellite rain** (`scripts/pardig.mjs`, `scripts/gsmap.mjs`): outside radar coverage the past hours use Google DeepMind PARDIG (0.1°, every 15 min, read anonymously from the public bucket `gs://pardig_1`, averaged to hourly means), with JAXA GSMaP Gauge_NOW/NRT for the newest hours PARDIG has not published yet (it runs ~4–5 h behind) and as the fallback. Against 675,601 ThaiWater gauge-hours (9–15 Nov 2026) PARDIG caught 71 % of rain hours ≥ 0.5 mm/h with 52 % false alarms, GSMaP 44 % with 68 %. Both are logged in `rainobs-*.csv` (`pardig_cell`, `pardig_fine`) and scored daily against the gauges over 14 days; the page goes back to GSMaP by itself if PARDIG stops catching at least as many rain hours with no larger share of false alarms. PARDIG takes ECMWF fields among its inputs, so it is not used as the truth for fitting or judging ECMWF rain corrections (radar and gauges are).
- **PM2.5 correction v2, a candidate beside the live one** (`scripts/ml2.mjs`): in the first 47 days hours ≥ 37.5 µg/m³ were forecast far too low (measured 50, page 30 at 24 h; `analysis/highpm_replay.py`). Two causes: the live correction learns on ln(PM+1), which gives the median and pulls high values down, and it does not know a station's own habits (the peaks are short, local and recur at the same hours). v2 uses the same experts with the error in µg/m³ as the target and five station-history inputs known at issue time (same hour on the newest known day and the day before, 24-h maximum, 72-h 90th percentile, 7-day mean at that hour). It is computed and logged every hour (`correctedML2`; the live correction as `correctedML1`), and published only while a daily check over 14 days finds it at least as good as the live correction on all three counts: hours ≥ 37.5 caught, false-alarm share, RMSE.
- **Where the air comes from**: tap a place on the map → *Where is the air from?* draws an ensemble of 27 backward trajectories (48 h or 24 h) arriving at 100, 500 and 1500 m above ground, HYSPLIT-style (9 members per height with the winds read ±0.25° around the parcel), from ECMWF winds at 10 m, 100 m, 925, 850 and 700 hPa (`data/met-traj.json`, loaded on first use), and lists the countries the air passed over and the fire hotspots near the paths.
- **Ventilation**: map layer and place-card readout of the ventilation index (ECMWF boundary-layer height × 100-m wind, m²/s, drawn at 0.025° with the wind adjusted for terrain exposure and sheltering — MicroMet weighting of Liston & Elder 2006, within ±40 %; below 2,000 poor, 2,000–6,000 moderate, above 6,000 good — the US NMC air-pollution-potential criterion of Stackpole 1967 / Gross 1970); the forecast summary gives each day's mean.
- **Automatic refresh**: an open page checks `data/stamp.json` every 3 minutes and loads a new run in place (keeping the chosen hour and place); a new page version reloads the page.

## How it runs

| Part | Where | What |
|---|---|---|
| `scripts/update.mjs` | GitHub Actions, hourly | OpenAQ obs, CAMS, FIRMS → Kalman correction → `data/latest.json` |
| `scripts/verify.mjs` | same job | RMSE / bias / r by lead time → `data/verify.json` |
| `scripts/accuracy.mjs` | same job | 7-day accuracy per monitor for the public page → `data/accuracy.json` |
| `index.html` + `index_modern.html` | GitHub Pages (deployed by the workflow) | the site's default page (`/`) is the redesign (`index_modern.html` layout with the page code of `index.html`, built by `scripts/build_modern.mjs`); the original layout stays at `/classic.html`. Both read `data/*.json` and run the fire-smoke model in the browser |

Large, changing files (`latest.json`, `met.json`, `state.json`) are not committed: they are published to Pages and carried between runs in the Actions cache. The per-run logs (`data/history/YYYY-MM/`, last 35 days) live on the branch `history` and the ML training store (`data/mltrain/`, 2 years) on the branch `mltrain`; `main` keeps only the static files in `data/static/`.

No dependencies; Node 22 in the workflows (the SILAM step alone uses Python with netCDF4, installed when a new run is read).

## Setup

1. **Secrets** (Settings → Secrets and variables → Actions): `OPENAQ_API_KEY`, `FIRMS_MAP_KEY`.
2. **Workflow permissions** (Settings → Actions → General): *Read and write permissions*.
3. **Pages** (Settings → Pages): Source **GitHub Actions**. The hourly workflow publishes `index.html` and the data files as a Pages artifact.
4. Actions → *Hourly update* → *Run workflow* for the first run.

Tunable settings are in the `CFG` block at the top of `scripts/update.mjs` (area, grid step, Kalman Q/R, IDW radius, bias fade with lead time).

## Data sources

NASA FIRMS (VIIRS NRT) · OpenAQ v3 · Google DeepMind PARDIG (CC BY 4.0) · JAXA GSMaP · ThaiWater (HAII) rain gauges · RainViewer radar · Copernicus CAMS via Open-Meteo air-quality API · Open-Meteo forecast API · Natural Earth boundaries · CARTO / OpenTopoMap / Esri basemaps.

Screening tool: no plume rise, chemistry or wet removal in the fire-smoke model; check against ground monitors before acting on a warning.
