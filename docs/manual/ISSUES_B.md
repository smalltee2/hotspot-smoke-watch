บันทึกเพื่อส่งกลับให้ session ที่ดูแลโค้ด ไม่ได้แก้ไฟล์ใดใน repository ข้อมูลคือ branch `history` ที่ `bf4ceb8` และ `hindcast` ที่ `f726812`

## ข้อมูล

1. **ผล `pmHighCheck` ที่บันทึกของวันที่ 25 พ.ย. 2026 นับค่า spike ไปด้วย** `data/history/2026-11/ml-20261125.json` (`v2.check`) และ
   `silam/2026-11/ml-20261125.json` บันทึก RMSE 19.667 / 20.255 (CAMS) และ 21.101 / 21.129 (SILAM) ขณะที่วันก่อนและหลังอยู่ราว 8–12
   เมื่อคำนวณซ้ำบนหน้าต่าง 14 วันที่สิ้นสุด 25 พ.ย. 17:00 UTC เฉพาะแถวที่ออกตั้งแต่ 21 พ.ย. ได้ RMSE 19.39 / 19.97 ถ้ารวมค่า 904 และ 998 µg/m³
   ของ a4t:19t (24 พ.ย. 20–21 UTC) และ 8.94 / 9.99 ถ้าตัดออก แปลว่าวันนั้นการอ่าน log กลับ (`loadObsHourly`) ยังไม่ได้ตัด spike
   ผลการตัดสินวันนั้นไม่เปลี่ยน (v2 ไม่ผ่านอยู่แล้ว) แต่ตัวเลขในไฟล์นั้นไม่ควรนำไปเทียบกับวันอื่น
2. **log ของประตู nowcast ยังไม่มี** `ml-YYYYMMDD.json` ถึง 27 พ.ย. ไม่มีคีย์ `nowcast` และ `state.pmNow.check` ไม่ได้อยู่ใน git
   คอลัมน์ `correctedPre` / `correctedNC` มีเพียง 2 รอบ (28 พ.ย. 01 และ 02 UTC) ยังไม่มีค่าวัดมาตรวจ การตรวจทั้งหมดในบทจึงใช้แถวที่สร้างใหม่แบบ `pmNowCheck`
3. **`rainfc-20261116.csv` มีแถวที่จำนวนคอลัมน์ไม่ตรงกับหัวตาราง** หัวมี 12 คอลัมน์ ตั้งแต่บรรทัด 7130 มี 13 คอลัมน์ (คอลัมน์ `ecmwf_shift_pure_mmh` ถูกเพิ่มกลางวัน)
   `pandas.read_csv` อ่านไม่ได้ ส่วน `csv.DictReader` (ที่ `fit_rain_blend.py` ใช้) อ่านได้แต่ค่าคอลัมน์ที่ 13 ไปอยู่ใต้คีย์ `None`
   ควรเขียนหัวตารางใหม่เมื่อคอลัมน์เปลี่ยน (เช่น เริ่มไฟล์ใหม่) หรือบันทึกไว้ในเอกสารของ log
4. **แถว `gauge` ใน `rainobs-*.csv` ไม่มี `station_id`** (ว่าง) ต้องใช้ lat/lon เป็นรหัสมาตรวัด ถ้ามีมาตรวัดสองตัวพิกัดซ้ำกันจะแยกไม่ได้
5. **PARDIG และ GSMaP ซ้อนกันเพียง 3 ไฟล์รายวัน (16–18 พ.ย.)** PARDIG เริ่มถูก log ในไฟล์ 16 พ.ย. ส่วน GSMaP ว่างตั้งแต่ไฟล์ 19 พ.ย. (JAXA ปิดระบบ)
   `obsRainCheck` ที่ต้องการแถวที่มีทั้งสองค่าจึงจะได้ `decided: false` ไปจนกว่า GSMaP จะกลับมา และหน้าเว็บใช้ PARDIG ตามค่าเริ่มต้น
   (บันทึกไว้เพื่อให้เอกสารภาค C อธิบายสถานะนี้ได้ถูก)
6. **ขั้น fire assimilation ไม่มีผลใน log ปัจจุบัน** `correctedA` ต่างจาก `corrected` เฉลี่ย 0.002 µg/m³ (สูงสุด 15.5) และ `blend24A` = `blend24`
   ไม่ใช่ bug (แทบไม่มีไฟใน ต.ค.–พ.ย.) แต่ประเมินขั้นนี้ไม่ได้จนถึงฤดูหมอกควัน `map-*.csv` มีรุ่น `mapA` เพียง 497 จาก 839 รอบ ไม่พบคำอธิบายในโค้ดว่าทำไมบางรอบไม่มี
7. **ML ไม่ทำงานที่สถานีค่าเฉลี่ย 24 ชม.** `correctedML` และ `blend24ML` ว่างทุกแถวที่ `obs_basis = 24` (BMA และสำเนา OpenAQ) ถ้าตั้งใจควรระบุใน README ว่า ML ใช้กับสถานีรายชั่วโมงเท่านั้น
8. **ช่วงที่เก็บ log สั้นกว่าบันทึกการประเมินที่ README อ้าง** README อ้าง "owner's live-evaluation record (2 Oct – 25 Nov 2026, 76 monitors)" แต่ branch `history`
   เก็บเพียง 35 วัน (รอบตั้งแต่ 24 ต.ค. 2026) และไฟล์รายเดือน `fcst-2026-10.csv` มีเพียง 1 ต.ค. (รูปแบบ 6 คอลัมน์) จึงคำนวณตัวเลขนั้นซ้ำจาก `history` ไม่ได้
   ควรเก็บสรุปผลรายเดือน (หรือสำเนา log) แยกไว้ก่อนที่ log จะถูกลบ
9. **SILAM: ML v2 แทบเท่ากับ v1** ในทุกวันที่บันทึก (เช่น 27 พ.ย. จับได้ 1,105 เทียบ 1,099, FAR 75.5 เทียบ 75.0 %, RMSE 12.224 เทียบ 12.118) ขณะที่ฝั่ง CAMS v2 ต่างจาก v1 มาก
   อาจเป็นพฤติกรรมที่ถูกต้อง แต่ควรตรวจว่า v2 ของ SILAM ได้เรียนรู้จริง (เช่น น้ำหนัก experts ใน `silam/…/ml-*.json`)
10. **สถานี a4t:19t ไม่ส่งค่าวัดอีกหลัง 24 พ.ย. 2026 21 UTC** จนถึงเวลาที่ตัดข้อมูล แต่ยังมีค่าพยากรณ์ที่ใช้ Kalman bias ค้างอยู่ (เผยแพร่สูงสุด 90.3 µg/m³ ที่ lead 1 ชม.)
    จนกระทั่ง reset วันที่ 27 พ.ย. เป็นตัวอย่างของสถานีที่หยุดส่งค่าแต่ bias ยังคงอยู่ อาจพิจารณาให้ bias ของสถานีที่ไม่มีค่าวัดใหม่ลดลงตามเวลา
